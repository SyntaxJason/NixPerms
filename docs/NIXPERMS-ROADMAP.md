# NixPerms development roadmap

## Product rule

NixPerms must remain fully usable with only a supported SQL database. Redis, RabbitMQ,
a standalone daemon or a hosted NixPerms service may reduce propagation latency or add
management features, but none of them may become a correctness dependency.

The permission check itself is always local. A server tick, command permission check or
plugin API call must never wait for SQL, another Minecraft server, a proxy or a relay.

## Phase 0 — fast and correct local engine

Status: started in the current source tree.

Completed foundations:

- Immutable character-trie lookup for exact and hierarchical wildcard rules.
- No wildcard `substring` or concatenation work in the normal permission hot path.
- One immutable user state containing model, context, permission snapshot, metadata and revision.
- Revision-checked snapshot publication so an outdated calculation cannot overwrite newer state.
- Separate storage and compute executors.
- Parallel user snapshot rebuilding after a group mutation.
- Refresh coalescing for bursts of context and attachment updates.
- Sync-batch coalescing for repeated user/group invalidations.
- Hierarchical, typo-tolerant command completion and a Paper permission-node catalog.

Remaining Phase 0 work:

- Add JMH benchmarks for exact hit, exact miss, wildcard hit and global wildcard.
- Add allocation assertions with JFR or async-profiler in the benchmark profile.
- Build reverse dependency indexes from group to child groups and loaded users.
- Intern identical group and user snapshot structures to reduce memory on large networks.
- Add stress tests for simultaneous user edits, group edits, context changes and attachments.
- Remove or archive experimental modules that are not part of the Maven reactor.

Exit gate:

- Exact and wildcard checks allocate 0 B/op for already-normalized nodes.
- No locks, database calls, futures or inheritance traversal in `hasPermission`.
- Group updates rebuild only affected loaded users.
- Every state publication is revision-safe under concurrent changes.

## Phase 1 — reliable database-only synchronization

The database remains the durable source of truth. The outbox becomes revision based:

- A global monotonic revision for ordering and recovery.
- An entity revision for each user and group.
- Event IDs for deduplication.
- Persisted node cursors or deterministic recovery cursors.
- Gap detection and `SNAPSHOT_REQUIRED` recovery.
- Bounded replay batches.
- PostgreSQL `LISTEN/NOTIFY` as an immediate wake-up signal.
- Adaptive polling for MySQL and MariaDB.

A notification never carries authoritative permission state. It only tells another node
which entity revision to load from SQL. Missing, duplicate and reordered signals therefore
remain recoverable.

Exit gate:

- A node may be offline longer than the outbox retention and still recover automatically.
- Duplicate and reordered messages cannot roll state backwards.
- Database-only propagation is immediate on PostgreSQL and efficient on MySQL/MariaDB.

## Phase 2 — optional NixLink acceleration

NixLink is an optional binary invalidation transport. The recommended topology is a small
embedded hub rather than a self-organizing full mesh:

- Velocity or BungeeCord can host the embedded hub.
- A Paper node can host it when no proxy is present.
- Every node keeps one primary and optionally one fallback connection.
- SQL revisions and replay remain the correctness layer.
- Hub loss automatically falls back to database-only synchronization.

Security requirements:

- TLS by default.
- Challenge-response HMAC with nonces; never transmit the shared secret itself.
- Cluster ID, node ID, instance ID and protocol version in the handshake.
- Maximum frame sizes, handshake deadlines and connection rate limits.
- Secret rotation with current and next keys.

No adaptive delegate election or complex multi-mesh is planned until measurements prove
that a relay topology is insufficient.

## Phase 3 — optional hosted relay

A public relay operated by the NixPerms project can simplify NAT, Docker and small-network
setups. It remains optional and carries only encrypted invalidation envelopes.

- Outbound TLS connections only.
- End-to-end cluster encryption.
- No database credentials.
- No durable permission data.
- Automatic fallback to embedded hub or database-only mode.
- Clear telemetry opt-in and transparent retention policy.

## Phase 4 — web editor and control plane

The old experimental web module is not the basis for the new editor. The replacement uses
short-lived editor sessions and revisioned changesets:

- Svelte frontend.
- One-time, expiring session tokens generated by `/nixperms editor`.
- Draft changes before commit.
- Optimistic concurrency with explicit conflict views.
- Permission explanation: exact source, wildcard source, group chain, context and attachment.
- Change simulation before apply.
- Audit log and targeted rollback.
- Group comparison, bulk editing and plugin permission browsing.
- Optional collaboration without granting the browser direct SQL access.

## Phase 5 — role model and migration

Keep the simple public model while allowing future expansion:

- Exactly one primary rank.
- Zero or more persistent traits/secondary roles.
- Runtime attachments remain separate.
- LuckPerms importer with a dry-run report and conflict mapping.
- Backwards-compatible migration from the current single-secondary schema.
